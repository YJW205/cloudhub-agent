# Day 7 · 01 项目复盘：云枢 CloudHub 产品文档助手

> 这是你面试时"讲项目"的完整底稿。目标：5 分钟内讲清架构、亮点、踩坑。

## 一句话介绍（面试开场用）

> "我做了一个基于 LangGraph 编排的企业知识库智能助手，叫云枢产品文档助手。它把 RAG 检索、工具调用、多轮记忆三种能力合在一个 Agent 图里：模型自主决定什么时候查知识库、什么时候算费用，整个流程用 LangGraph 的条件路由控制循环，支持跨会话记忆。核心特点是 Agentic RAG——不是所有问题都固定先检索，而是让模型自己判断。"

## 架构总览

```
用户问题 ──> START
               │
               ▼
         ┌─ agent（模型思考：LLM + bind_tools）────────────┐
         │    │ 条件路由 should_continue                  │
         │    ├── 有 tool_calls ──> tools（执行工具）──────┘
         │    │                       │
         │    │                       ├─ retrieve：Chroma 知识库检索（Agentic RAG）
         │    │                       ├─ subscription_cost：套餐费用计算
         │    │                       └─ check_api_error：API 错误码查询
         │    └── 无 tool_calls ──> END（输出回答）
         └────────────────────────────────────────────┘
    + SqliteSaver checkpoint：thread_id 会话隔离 + 跨运行记忆
```

## 4 个可讲的技术决策（深挖点）

### ① 为什么 Agentic RAG 而不是固定流程 RAG？
普通 RAG 是"每个问题先检索 → 再回答"的固定管道；Agentic RAG 把检索封装成工具，由模型判断"这个问题要不要查文档"。好处：闲聊和文档外问题**不浪费检索**，费用计算类问题**走工具不走文档**，模型有自主决策空间。这是 LangGraph agent 循环天然支持的——检索只是 tools 里的一员。

### ② 工具容错怎么做的？（你踩过的真实坑）
DeepSeek 一次构造多组工具参数时偶发传错导致调用失败。方案两条：
1. **system prompt 约束**："一次只调用一个工具、数字参数必须纯数字"
2. **容错循环**：工具抛异常 → 错误以 ToolMessage 回传给模型 → 模型自纠重试 → 设最大轮数防死循环
> 面试话术："多工具并行在 DeepSeek 上不稳定，我通过约束串行 + 错误回传重试解决，生产级 Agent 都要考虑这个。"

### ③ 结构化输出的坑
DeepSeek 不支持 `with_structured_output` 默认的 json_schema 格式，必须 `method="function_calling"`。踩过才知道——这也是"调研 LLM 能力边界"的体现。

### ④ checkpoint 为什么优于"存消息"？
Checkpoint 存的是**整张图每一步的状态**，不只是消息列表。好处：多轮记忆、会话隔离（thread_id）、还能支持**断点续跑 / 人工介入**（图的中途状态可以恢复）。

## 踩坑清单（简历"抗压"素材）

1. `SqliteSaver.from_conn_string` 传**文件路径**而非 `sqlite:///` URL（Windows 盘符路径坑）
2. BGE embedding 与 transformers 5.x 不兼容 → 锁定 `sentence-transformers==4.1.0` + `transformers<5`
3. huggingface.co 直连超时 → `HF_HUB_OFFLINE=1` + `HF_ENDPOINT=https://hf-mirror.com` + 本地缓存
4. DeepSeek json_schema 响应格式服务端拒绝 → `method="function_calling"`
5. `with SqliteSaver(...)` 块结束关闭连接 → 直接持有 conn 供程序生命周期使用
